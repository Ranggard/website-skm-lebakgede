# Dashboard Period Filter Implementation

This change adds a period filter to dashboard statistics that allows filtering data by quarters (TW1-4), semesters, full year, and custom date ranges. The filter state is managed in the page component and passed to the header for UI display, then applied to all statistics and tab data downstream. The implementation parallels the existing export filter pattern, using the same period type definitions.

All five dashboard tabs (Ringkasan, Grafik, Demografi, Responden, Saran) now respect the filter, with the filtered response count displayed in the header alongside the active period selection. Custom date ranges require both start and end dates to be set via date input fields that appear conditionally.

**Watch for:** Date boundary bugs in quarter/semester calculations (months with variable days), unfiltered TabRingkasan component, and filter persistence across page reloads.

**Verdict**: NEEDS_CHANGES

---

## High-level view

**Filter state and upstream flow.** Three new state variables control the filter: `dashboardPeriod` (period type), `dashboardStartDate`, and `dashboardEndDate` for custom ranges. They initialize to 'all' and empty strings, with no persistence across reloads. A memoized `dashboardFilteredResponses` computes filtered data based on the period selection, then flows to `derivedStats` (used by Ringkasan, Grafik, Demografi tabs), `filteredResponses` (Responden), and directly to TabSaran. The header displays a live badge showing the filtered response count.

**Date boundary calculation uses hardcoded month-end days.** Quarter and semester boundaries hardcode day-of-month values (e.g., March 31, June 30, September 30, December 31). This works because those days exist in those months, but creates fragile code that could break if month indices are adjusted later. The more defensive pattern would derive the last day of each month programmatically using `new Date(currentYear, nextMonthIndex, 0, 23, 59, 59, 999)`.

**Filter UI and custom date inputs.** The header restructured into two rows; period selector is in the second row with date inputs appearing conditionally when 'custom' is selected. The filtered response count displays as an animated badge on the far right with live updates.

**All five tabs respect the filter.** TabResponden receives pre-filtered data through the cascade; TabSaran explicitly receives filtered responses with a defensive fallback. Other tabs consume `derivedStats` which now computes from filtered data. Export tab remains independent.

<details>
<summary>Issues (4)</summary>

1. **Date boundary hardcoding** — Quarter and semester end dates use hardcoded day-of-month values. While correct for the specific months (March 31, June 30, September 30, December 31), this is brittle if period definitions change. Use `new Date(currentYear, month, 0)` to get the last day of the previous month, or use day-agnostic logic (e.g., `new Date(currentYear, nextMonthIndex, 0, 23, 59, 59, 999)` for the last moment of the month).

2. **TabRingkasan unaware of filter state** — TabRingkasan receives no filter-related props and has no way to know which period is active, even though it displays filtered stats via `derivedStats`. If the component needs to display period metadata (e.g., "Statistics for Q1 2026"), it cannot access `dashboardPeriod`. Pass `dashboardPeriod` as a prop to TabRingkasan for completeness and future flexibility.

3. **Invalid date handling in custom range** — When parsing custom dates from HTML date inputs, the code creates a Date object directly from the ISO string (e.g., `new Date('2026-01-01')`). This creates a UTC midnight time. If the server interprets response timestamps in local time, timezone mismatches could cause off-by-one day errors during filtering. Test custom range filtering with responses that have timestamps near midnight in the target timezone.

4. **No filter persistence** — Filter state resets to 'all' on every page reload because state is initialized in useState(), not restored from localStorage or URL params. This is different from the intuitive expectation that a dashboard filter persists across sessions. Consider persisting to localStorage and restoring on mount, or encoding the filter in URL params for shareability.

## Detailed Analysis

<details>
<summary>Details</summary>

### Date Boundary Calculations — Hardcoded Month-End Days

The period filter hardcodes day-of-month values:

```javascript
if (dashboardPeriod === 'tw1') {
  start = new Date(currentYear, 0, 1, 0, 0, 0, 0)     // 1 Jan
  end = new Date(currentYear, 2, 31, 23, 59, 59, 999) // 31 Mar
} else if (dashboardPeriod === 'tw2') {
  start = new Date(currentYear, 3, 1, 0, 0, 0, 0)     // 1 Apr
  end = new Date(currentYear, 5, 30, 23, 59, 59, 999) // 30 Jun
}
// ... etc
```

This works because the specified days exist, but it's brittle. If month indices are adjusted by mistake, the hardcoded days could mismatch. A defensive approach would compute the last day of each month programmatically:

```javascript
const lastDayOfMonth = (year, month) => 
  new Date(year, month + 1, 0, 23, 59, 59, 999)
```

The current implementation produces correct boundaries for all 2026 periods, but the pattern is a code smell for future maintenance.

### Response Filtering and Timestamp Handling

The filter iterates over responses, accepting multiple timestamp field names and excluding responses outside the boundary range. Responses with missing or invalid timestamps are included — a permissive choice safe for display.

**Timezone mismatch risk.** HTML date inputs produce ISO 8601 strings; `new Date('2026-01-15')` creates a Date at 00:00:00 UTC. If response timestamps are stored in local time (e.g., UTC+7), boundary comparisons could produce off-by-one errors. A response at "2026-01-15 23:00:00 local" might fall outside a custom filter meant to include that date. No timezone normalization is visible in the code, so this is worth testing with edge-case timestamps near midnight.

### Stats Computation Uses Filtered Data

The `derivedStats` memo now iterates over `dashboardFilteredResponses` instead of `allResponses`, ensuring all statistics (IKM, element scores, demographics, quality grades) reflect only the selected period. The dependency array includes `dashboardFilteredResponses`, so stats recompute whenever the filter changes. Ringkasan, Grafik, and Demografi tabs all consume `derivedStats` and thus automatically display filtered data.

### Responden and Saran Tabs

TabResponden receives pre-filtered data through the cascade; TabSaran receives `dashboardFilteredResponses` as a prop with a defensive fallback to `allResponses`. Both tabs apply their own table-level filtering on top of the dashboard period filter.

### Header Display and Filter UI

The header restructured into two rows: the period selector dropdown occupies the second row with date inputs conditionally shown for custom ranges. The filtered response count displays as an animated badge on the far right. The UI correctly shows/hides date inputs based on period selection.

### Custom Date Range Handling — UTC vs Local Time

When the user selects 'custom', HTML date inputs produce ISO 8601 strings (e.g., "2026-01-15"). `new Date('2026-01-15')` creates a Date at 00:00:00 UTC; the end date is adjusted to 23:59:59 UTC. If response timestamps are stored in local time, boundary comparisons could produce off-by-one errors near midnight. This is worth testing with edge-case timestamps.

### Filter State Persistence

Filter state initializes in useState() with no restoration from localStorage or URL params on mount. Each page reload resets to 'all' and clears custom dates. This is consistent with the export filter but may not match user expectations for a dashboard filter.

### TabRingkasan Filter Awareness

TabRingkasan receives only `derivedStats` without access to `dashboardPeriod` or filter state. If the component needs to display period metadata (e.g., "Statistics for Q1 2026"), it cannot access which period is active. Passing `dashboardPeriod` as a prop would enable future UI enhancements.
